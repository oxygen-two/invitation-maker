# Internationalization (i18n)

The studio, the shared/public viewer, the standalone-download viewer, and the landing/guide/legal site chrome support Korean and English. There is no i18n library and no bundler: a plain dictionary plus `data-i18n` attributes, matching the rest of this project's no-build approach.

## Files

```
assets/i18n/
  i18n.js                 the engine — resolution, persistence, lookup, Intl formatting
  dictionary-ko.js         Korean UI strings (studio chrome, dialogs, error pages)
  dictionary-en.js         English UI strings, same key set as dictionary-ko.js
  dictionary-site-ko.js    Korean copy for the landing page, guide, privacy and terms (the `site.*` namespace)
  dictionary-site-en.js    English copy for the same pages, same key set as dictionary-site-ko.js
  content-en.json          English overlay for sample/demo invitation content
```

`i18n.js` knows nothing about which strings exist; it only resolves a language and looks keys up. `dictionary-ko.js` and `dictionary-en.js` self-register with `InvitationI18n.register(language, dictionary)` when loaded, so adding both script tags is what makes a language available at all — the engine has no other way to discover a dictionary. `dictionary-site-ko.js` and `dictionary-site-en.js` are not a second, independent dictionary: each re-registers its language with the corresponding main dictionary spread underneath its own `site.*` namespace, so a page that skips the two site files still gets studio/error-page strings, just no `site.*` keys. Korean is the base language (`DEFAULT_LANGUAGE = "ko"`).

Seven pages load the engine, each calling `InvitationI18n.init()` once its scripts are in place:

- **Main dictionaries only** (`i18n.js`, `dictionary-ko.js`, `dictionary-en.js`): `studio.html`, `viewer.html`, `shared.html` — the editor and public-viewer surfaces have no `site.*` copy to show.
- **Main and site dictionaries**, in that fixed order (the three above, then `dictionary-site-ko.js`, `dictionary-site-en.js`): `index.html`, `guide.html`, `privacy.html`, `terms.html`.

Keeping the engine separate from the dictionaries means the resolution logic (query string, storage, browser preference, fallback) can be tested without a single translated string, and it means adding a language is purely additive: a new `dictionary-xx.js`, an entry in `i18n.js`'s `LOCALES` map, and (if the demo content should be localized too) a `content-xx.json`. Nothing else in the codebase needs to change.

## How a language is chosen

`InvitationI18n.resolve()` checks, in order:

1. `?lang=` in the URL — honored for that page view only, never written to storage. A link someone shares can show its language for one visit without overriding the language the visitor had already chosen on their own device.
2. The stored override (`localStorage["invitation-maker.language"]`) — the only thing the language switcher itself writes, so it is the only signal that represents a decision made on this device.
3. `navigator.languages`, first entry that matches a supported language.
4. Korean, the product's home language and the language the templates were designed around.

`InvitationI18n.init()` calls `resolve()` once at boot and applies the result. It only persists to storage when the resolved source was itself `"stored"` — a one-off `?lang=` link never gets written back, and a first-time visitor's browser-language guess isn't silently locked in until they actually touch the switcher (`#language-select` in the studio header, wired in `assets/studio/app.js`).

Switching language calls `setLanguage()`, which re-runs `applyDom()` over every `[data-i18n]` / `[data-i18n-attr]` node, updates `<html lang>`, and updates `document.title` if the page names a `data-i18n-title` key. `applyDom()` is what actually rewrites the visible DOM; it also runs once at boot and is the reason a page with JavaScript disabled still shows correct Korean — the inline text in `index.html`/`viewer.html`/`shared.html` **is** the Korean copy, and English only appears once the script runs.

## Adding a language

1. Add an entry to `LOCALES` in `assets/i18n/i18n.js` (`locale` for `Intl`, `label` in the language's own words, `hour12` for its clock convention).
2. Create `assets/i18n/dictionary-xx.js` with the same key structure as `dictionary-ko.js`. `tests/i18n.test.js` asserts every registered language ships an identical set of leaf keys — a dictionary with a missing key fails the test, not silently at runtime.
3. Load the new `<script>` tag next to the existing ones on every page that loads the engine: `studio.html`, `viewer.html`, and `shared.html` always; `index.html`, `guide.html`, `privacy.html`, and `terms.html` also need the new site dictionary's own script tag if the language should carry `site.*` copy too.
4. Optionally add `assets/i18n/content-xx.json` (see below) so the studio's sample/demo invitations read naturally in the new language too. Without it, the studio still works — the gallery samples just stay in Korean for that language.

A missing dictionary key is deliberately not silent: `translate()` returns the key itself (e.g. `gallery.showAll` printed literally) rather than falling back to Korean. A Korean fallback would look like a plausible, finished translation; the raw key is obviously broken and gets fixed. This is a last resort, not the normal path — the key-parity test is what's supposed to catch it first.

## What is translated, and what deliberately is not

**Studio chrome, dialogs, and error pages** — every button, label, and status message the studio itself displays — comes from the dictionaries and switches live with the language selector.

**The invitation's authored content follows the language exactly until the author writes something of their own — then it never translates again.** A sample title, host name, or message the studio put on the page is not fixed to the language it started in: switching the studio's language, or restoring a draft that was written in a different studio language, rewrites the sample's title/host/message from the active design's own localized preset. That rewrite runs only when the form still reads back exactly as it did the moment the sample was applied — `showsUntouchedSample()` compares the current form against the baseline `captureAppliedBaseline()` took at that moment, via `PresetApplication.isDirty()` (`assets/studio/app.js`). The instant an author edits any of those fields the comparison stops matching, and from then on the words are the author's, not the studio's: no later language switch, undo, or design change rewrites them again, in the studio, the standalone export, or the public viewer (PRs #45, #53). A restored draft is asked the same question at boot — not against itself, since everything compares equal to itself, but against the sample it would have been rebuilt from in the language it was written in — so an untouched draft still re-localizes to the studio's current language on open, while a personally written one opens exactly as it was saved. Only the *chrome around* an invitation — its own baked labels like "안내" or a "주소 보기" button, which come from the dictionary and are rendered once at build time — is a plain, unconditional language switch with no such history to consult.

**Generated/sample dates go through `Intl`; a typed `dateLabel` never does.** `InvitationCore` stores a language-neutral `dateTime` for sample content and formats it per-language with `formatSampleDate()` (`Intl.DateTimeFormat`, per-locale month/weekday/day-period and 12h/24h conventions — see `LOCALES[lang].hour12`). The moment an author edits the date field, the invitation stores their own `dateLabel` string instead, and every later language switch renders that string byte-for-byte. This is why the field is asymmetric: dates you never touched update when you change the studio's language; dates you did touch do not.

**Sample content is per-language, structurally locked to the Korean original.** `invitation-data.json` is the single source of structure — every template ID, item ID, effect, font, coordinate, and zoom level. `assets/i18n/content-en.json` is an overlay keyed by the same IDs that carries only translatable leaves (`title`, `subtitle`, `host`, `location`, `message`, per-item text, occasion/template names). `assets/studio/app.js`'s `localizeSampleInvitation()` / `localizeCatalogData()` merge the overlay onto the base data at runtime; nothing about which templates exist, what an item's type is, or how it renders can drift between languages because the overlay simply has no field for those. Because the overlay is fetched lazily (`loadContentOverlay()`), a demo/gallery viewed in Korean never fetches it at all.

**A translated sample is localized, not just translated.** The Korean samples are written for Korea and stay that way; the English overlay names region-neutral places, hosts and phone numbers instead ("Rooftop lounge", "Riverside park", "+1 555 010 0000"), because an English reader opening the studio to a Seoul district learns first that the product is not for them. `tests/i18n.test.js` fails on a Seoul district name, on `Seoul`/`Gangnam`, and on a `010-` phone number anywhere in `content-en.json` or in the English `invitation.default*` values. The exception is the occasions that are themselves Korean traditions — `gohui`, `hwangap`, `first-birthday` — where the names, dishes and customs in the sample are the point of the design.

**Decorative English typography is not translated and is not meant to be.** The templates print course labels (`MEET`, `CAFE`, `WALK`, `DINNER`, `DRINK`, `ACTIVITY` — see the comment in `assets/studio/app.js`) and section markers in the same letterspaced English used across the template designs. These are typographic convention on a Korean invitation, not UI copy; translating them would break the layouts they were set for.

## Errors and defaults resolve through dictionary keys, not baked strings

Photo upload, IndexedDB, and map-lookup failures used to throw Korean sentences directly, which meant an English-language studio still showed Korean on failure. `assets/media/image-tools.js`, `assets/storage/invitation-storage.js`, and `assets/integrations/map-location.js` now throw errors carrying only a machine `code` (for example `type`, `sourceSize`, `decode`, `encodedSize`, `generic`); `assets/studio/app.js` maps that code to a dictionary key under `errors.image.*` at the point of display, e.g. `t("errors.image.type")`. Nothing upstream of the display layer knows or cares which language is active.

The same rule applies to the invitation a first-time visitor sees before typing anything: `assets/invitation/core.js` resolves its title, subtitle, location, message, and per-course place/note text through `invitation.defaultTitle`, `invitation.defaultSubtitle`, `invitation.defaultLocation`, `invitation.defaultMessage`, and `invitation.defaultCourse{Meet,Cafe,Walk,Dinner}{Place,Note}` for the active language at normalize time, instead of a Korean literal that only translated once an author started editing.

## Standalone downloads bake their chrome at export time

A downloaded HTML file has no engine attached and travels on its own — it may be reopened years later on a machine with no network access. `InvitationCore.buildStandaloneHtml(invitation, { language })` therefore renders the invitation's own chrome once, in whatever language the studio was set to at the moment of export, and writes it to `<html lang="...">`. `InvitationCore.readStandaloneLanguage()` reads that attribute back, which is how re-importing a previously downloaded file into the studio (or the studio's own live preview, which renders through the same `buildStandaloneHtml` call into an iframe) reproduces the file as originally exported instead of re-languaging someone's finished invitation to the studio's current setting. Files exported before this existed have no such attribute and default to `lang="ko"` — which is exactly what they were built in, so old exports still round-trip correctly.

## Published (shared-link) invitations: chrome and content follow different people

This is the one place where two different "whose language is this" answers are both correct at once, for two different parts of the same page, and getting them backwards is the mistake this design exists to prevent (see the comment block at the top of `assets/publishing/shared-invitation.js`):

- **The page chrome** — the loading line, and the not-found / expired / failed panels a guest sees if the link is bad — is the product speaking to a *guest* who followed a link and never touched the studio. That chrome follows the guest's own browser language (`shared.html` runs `InvitationI18n.init()` before anything else loads).
- **The invitation rendered inside the frame** is rendered in the language its *author* published it in — **not** the guest's browser language. Rendering it in the guest's language would mean silently translating a stranger's finished invitation, which is precisely the behavior the authored-content rule above forbids.

The author's language reaches the guest as a field of its own, carried alongside the invitation rather than inside it, because it describes the rendering and not the content:

1. `assets/publishing/publishing.js` puts `language: InvitationI18n.getLanguage()` — the studio language at the instant Publish is pressed — into the publish payload, beside `invitation`.
2. `server/validation.cjs` accepts it only when it is one of the languages the engine registers (`SUPPORTED` in `assets/i18n/i18n.js`, today `ko` and `en`); anything else is a `400 BAD_REQUEST`, and an absent one defaults to `ko`. Adding a third language therefore stays the one-file change it is today.
3. The stored record keeps it, and `GET /api/invitations/:id` always answers it beside the invitation.
4. `assets/publishing/shared-invitation.js` hands it to `buildStandaloneHtml`, which stamps it into `<html lang>` exactly as a downloaded standalone file does.

A publication made before the field existed carries no language at all. Both the read path and the viewer answer `ko` for it, which is the language every one of them was in fact authored and previewed in, so nothing is back-filled.

A guest with an English browser opening a Korean invitation's public link therefore sees English loading/error text and, once the invitation loads, an invitation still entirely in the Korean it was written in. The same guest opening an English author's link sees English on both sides.

## Error pages inline both languages, because the dictionary might not load

The static status pages (`404.html` and the rest, see `docs/error-pages.md`) cannot depend on `assets/i18n/i18n.js` or a dictionary script loading successfully — an error page is the moment when a network or asset fault is most likely, and it would be self-defeating for the page explaining that fault to depend on more requests succeeding. `scripts/build-error-pages.cjs` instead reads the `errorPages.<status>.*` namespace from both `dictionary-ko.js` and `dictionary-en.js` at build time and inlines both languages' full copy — eyebrow, title, description, hint, action, reload label — into each generated page as a `<script type="application/json" data-error-copy>` block. A small inline script repeats `i18n.js`'s own resolution order (`?lang`, then `localStorage["invitation-maker.language"]`, then `navigator.languages`, then `ko`) to pick which language object to apply, entirely without loading the engine itself. The document's initial markup is Korean, so a browser with JavaScript disabled, a crawler, or a script that fails to run still reads a complete, real page rather than a blank or broken one.

## JSON-LD structured data stays in sync with the language switch

`index.html` and `studio.html` each carry one `<script type="application/ld+json" id="page-schema">` block, served in Korean so a crawler that runs no script still reads a real, complete description rather than a claim about a page it never rendered. A page that does run scripts rewrites the whole block — `description` (from the `meta.schemaDescription` dictionary key) and `inLanguage` — to whatever language `InvitationI18n.init()` resolved, then keeps it in step by subscribing to further language changes (`InvitationI18n.subscribe`). The rewrite parses and re-serializes the JSON rather than patching text, so nothing in a dictionary value can inject markup into the block. `guide.html`, `privacy.html`, `terms.html`, and the viewer/shared pages carry no such block; only the two pages a search engine is expected to index carry one.

## A title's own script decides its wrap rule, not the document language

An invitation's title is free text the author typed, so its script and the document's `lang` are two different questions — a Latin title inside a `lang="ko"` export is the ordinary case, not an edge case (see "What is translated" above). `template-renderers.js` and `intro-effects.js` test the title's own characters for Hangul and stamp the result onto the `<h1>` as `data-title-script="ko"` or `data-title-script="en"`, in both places a title renders: the card's hero and the intro overlay. CSS reads that attribute, not `[lang]`, to pick a title's wrap rule — `overflow-wrap: anywhere`, which a long unbroken Korean title needs, versus whole-word wrapping and `keep-all` for everything else. Reading `[lang]` instead would apply the wrong wrap rule to any title written in a script other than the one the invitation happens to be exported in.

## English regional date variants

`LOCALES.en` in `assets/i18n/i18n.js` carries `variants` keyed by lowercase region tag (`en-gb`, `en-au`), each overriding only `hour12` and `dateOrder` for `Intl`-backed formatting — a region is never allowed to change which dictionary is used, only how a date renders. `resolveDateFormat()` reads `navigator.languages` for a matching regional tag and applies its variant; an explicit `en-GB`/`en-AU` language tag is honored the same way, at its word. This is why a UK or Australian visitor's generated dates read `19 Dec 2026, 17:00` instead of the US default `Sat, Dec 19, 2026 · 5:00 PM`, while the UI language stays plain English throughout — `en-GB` and `en-AU` are date-formatting variants of `en`, not separate dictionaries.

## Occasion group keys

Every occasion in `invitation-data.json` carries a `group` (`celebrate`, `milestone`, `family`, or `gather`; an occasion with no recognized group falls back to `gather`). `assets/invitation/template-catalog.js`'s `getOccasionsByGroup()` returns only the groups that actually have occasions, in that fixed order, so the gallery's chip rows never print an empty group label. Each group's display name is a dictionary key — `gallery.groupCelebrate`, `gallery.groupMilestone`, `gallery.groupFamily`, `gallery.groupGather` — the same key set in both `dictionary-ko.js` and `dictionary-en.js`, checked by the same key-parity test as every other dictionary entry.

## Tests

`tests/i18n.test.js` covers key-count parity between `dictionary-ko.js` and `dictionary-en.js`, resolution order (`?lang=` > stored > `navigator.languages` > default), persistence rules, `Intl`-backed date/number/percent formatting per locale, and the `content-en.json` overlay's structural alignment with `invitation-data.json`. `tests/site-pages.test.js` runs the equivalent leaf-key parity check for `dictionary-site-ko.js`/`dictionary-site-en.js`, and separately asserts that every `data-i18n`/`data-i18n-attr`/`data-i18n-title` binding on `index.html`, `guide.html`, `privacy.html`, and `terms.html` names a key one of the site dictionaries actually ships. Run either with the rest of the suite:

```sh
npm test
```
